# ADR 0016: confirm 动作——事前拦截代替事后注入

- 状态：已接受
- 日期：2026-11-05

## 上下文

pi-cues 的全部注入都发生在 `tool_result`：命令已经跑完、文件已经读过，提示才随结果到达。对「提醒类」上下文这有一个结构性缺陷——**触发那一刻的执行本身就是该被提醒的那次执行**。典型场景：`docker build` 需要宿主机代理，inline cue 能把提示送进上下文，但第一次构建已经在没代理的状态下跑起来了，这一轮注定失败或白白耗时；提示要等到事后才生效。

事后注入做不到「先看提示，再执行」。需要一个新的 action：`confirm`，在工具执行**之前**拦截第一次匹配的调用，把提示作为拦截理由交给模型，模型读完后重发，重发即放行。

pi 的事件链恰好提供了这个钩子：`tool_call` 在每个工具调用执行前触发，handler 返回 `{ block: true, reason }` 即拦截，pi 把 reason 包装成 error tool result（`isError: true`）返回给模型——命令未执行，模型读到 reason 后可以调整并重发。

## 决策

新增 `action = "confirm"`：

- **事前拦截**：`tool_call` handler 匹配触发器（bash 用 `when.command` 词级前缀、path 工具用 `when.path`，匹配逻辑与其余 action 完全一致），首次匹配返回 `{ block: true, reason }`。reason 是一个 `action="confirm"` 的 `<pi-cues>` 信封，内容为提示模板渲染后的文本。
- **一次性，按内容寻址去重**：dedup 键沿用 ADR 0005（`confirm:{target}`），在 `tool_call` 内 claim。重发的调用到达时键已被占，直接放行——模型第二次发出同一命令时它真正执行。压缩后随会话状态重置，再拦一次。
- **提示模板可全局覆写，默认英文**。默认模板承担三重语义：未执行（防模型脑补结果）、不是权限拒绝且重试会正常执行（防模型当成被拒绕路）、必要时调整命令再重发（不只是盲重发）。模板必须包含 `{target}` 占位符；`[confirm] template` 仅全局配置可写——提示框架是 agent 主人的声音，克隆的项目无权改写（与 telemetry 同一先例）。
- **四类工具皆可**：bash（`when.command`）与 read/edit/write（`when.path`）。第一次编辑生成文件、第一次读敏感文件，与第一次跑慢命令同构。
- **单 target**：一次拦截只有一个理由，多 target 没有可预测的取舍顺序，校验期直接拒绝。
- **拦截时发 toast**（`confirm prompt shown for ...`），并记 telemetry；`/cues status` 显示 confirm 模板是默认还是自定义。

## 备选

- **继续用 inline 事后注入**：被否决。提示到达时被提醒的执行已经发生，对「先看提示再动手」类上下文（代理、耗时警告）结构性地晚一轮。
- **`terminate: true` 强制回合终止**：被否决。pi 支持 block 时顺带终止当前工具批次，但 confirm 的语义是「读提示→重发」，模型在同批次内自行重发即可，强制终止反而打断它的计划。
- **每会话多次拦截（每次都拦）**：被否决。那就成了权限系统的照妖镜——每条命令都要过两遍；confirm 的价值恰在「第一次看清楚，之后不再打扰」。
- **模板放触发器内逐条覆写**：被否决。逐条覆写意味着每条都要重写一遍「未执行/非拒绝/可重试」框架，任何一条漏写都会误导模型；全局一处模板，触发器只写差异文本。

## 后果

- 「先看提示再执行」类上下文获得确定性载体：代理配置、耗时警告、生成文件警示，都从「事后补救」变为「事前拦截」。
- 拦截代价是一次注定失败的调用（error result）——模型读 reason、重发，多一个来回。对每会话首次才触发的特性，这是可接受的上限。
- `tool_call` 匹配失败必须吞掉：pi 对抛错的 handler 按拦截处理（fail-safe），confirm 自己的 bug 不应变成硬拦截。
- 与 inline 的分工明确：上下文在执行**之后**仍有价值（习惯纠正、事后参考）用 inline；必须**先于**执行到达（否则该次执行就错了）用 confirm。
