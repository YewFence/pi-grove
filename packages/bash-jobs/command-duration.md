# 待实现：向模型报告慢命令的执行耗时

状态：暂缓实现。当前继续使用现有插件，本文件只记录需求和讨论中的实现方向。

## 当前行为

`src/index.ts` 已修正 TUI 的计时起点：只有调用真正进入 bash 的 `execute()` 后，内置渲染器才开始计算 `Elapsed` / `Took`，不计执行前的审批等待。这些数字只用于界面显示，不会自动进入模型上下文。

## 需求边界

- 让模型在命令结束时知道它实际运行了多久，重点覆盖慢命令。
- 转后台时不报告耗时；仍在运行的 `bash_wait` 结果也不报告耗时。
- 前台完成的命令随 `bash` 终态结果报告；后台命令随第一次取回的终态结果报告，不额外发送通知或唤醒模型。
- 后台时长从命令启动算到实际退出，包含转后台前的运行时间，不包含退出后等待模型查询的空档。
- 不把权限审批等待、`bash_wait` 单次等待时长当作命令执行时间。
- 范围限定于本插件执行的命令，不给其他工具增加通用耗时统计。
- 开关以后再考虑，本次需求不包含配置系统。

## 建议的输出

只在满足慢调用阈值的终态工具结果中，给模型追加一段独立文本，例如：

```text
测试通过

[Command execution time: 3.2s]
```

慢调用阈值建议先使用 1 秒；这个数值尚未最终确认，实现时再定。建议成功、非零退出和被终止的命令都使用同一阈值，不给快速失败额外增加例外。

## 实现方向

以下是尚未实施的方案，不是当前能力。

1. 复用进入真实执行后的计时边界及已有执行计时，不读取 TUI 渲染器的私有状态。
2. 前台命令在执行结束时固定耗时；后台 job 在进程实际结束时固定总耗时，后续查询只读取这个值。
3. 将需要报告的耗时存入终态工具结果的 `details`，随 session 保存。抛错路径通过 `tool_result` 钩子补齐元数据，保留原有失败语义。
4. 通过 `context_with_system` 仅在发给模型的结果副本中追加耗时文本，不改写原始命令输出，TUI 继续沿用现有渲染，避免重复显示计时。
5. 终态结果本身只交付一次；后续模型请求自然重用已有历史结果，不再追加新消息或重复修改保存的内容。

## 验证重点

- 慢命令的成功及失败结果携带模型可见的耗时，快命令保持原样。
- 长时间等待审批不影响报告的执行耗时；审批拒绝时不报告耗时。
- 无输出的慢命令仍能报告耗时。
- 转后台及仍在运行的查询结果不报告耗时，终态结果才报告总执行时长。
- 后台命令结束很久后才查询，报告的耗时仍以实际结束时间为准。
- 通过 `bash_kill` 取回终态结果时也遵守同一口径。
- 重复模型请求及会话恢复不会重复附加标记，原始工具输出和 TUI 显示不被修改。

## 已调查的替代方案

[pi-tool-duration](https://github.com/fitchmultz/pi-tool-duration) 已提供模型可见的工具耗时，但其口径是 `tool_execution_start` 到 `tool_execution_end` 的完整调用耗时，包含审批等执行前处理；后台任务测的是启动调用，而不是进程最终结束的总时长。因此它不直接满足这里的命令执行耗时需求，但其“只修改模型上下文副本”的交付方式可以借鉴。
